A FHIR terminology server for SNOMED CT, LOINC, ICD and every FHIR code system, on ordinary hardware.

FerroTERM serves the HL7 FHIR terminology API on R4, R4B, R5 and the R6 ballot from one binary over an index built once per release and read at startup. No JVM, no search cluster. You bring the release you are licensed for; the build tool turns it into an index; the server answers from it.

Run the quickstart See the benchmarks

A server image and a console image on GHCR and the ferroterm and ferroterm-build binaries for Linux, built at SLSA Build Level 3, and the release readers and the terminology engine on crates.io.

What it answers

One seam, many code systems

Every code system reaches the FHIR operations through the same provider seam, so nothing in an operation is a special case for one system.

FHIR terminology API

The terminology operations

$lookup, $validate-code, $subsumes, $expand, $translate and $closure, answered from the index the server read at startup.

R4, R4B, R5 and R6

Every FHIR version in its own shapes

/r4, /r4b, /r5 and /r6, in JSON or XML, each version's parameter set generated from HL7's own packages.

ECL and implicit value sets

Value sets

Value sets by composition, the implicit value sets of SNOMED CT, LOINC, RxNorm and ICD-11, and the SNOMED CT Expression Constraint Language over the inferred hierarchy.

Code systems

The releases you license

SNOMED CT, LOINC, ICD-10 and ICD-11, RxNorm, the Dutch national sets and any FHIR CodeSystem, each built from its own release, with UCUM and the registries inside the binary.

Stored resources

Value sets you write

Code systems, value sets and concept maps written to the server and kept with their history, when you name a database for them.

National terminology services

Sync from upstream

The sync service reads a national terminology service's feed on a schedule, builds what you subscribed to and asks the server to reload, in one direction only.

SNOMED CT, LOINC, UCUM, BCP 47, BCP 13, ISO 3166-1, ICD-10 (WHO), ICD-10-NL, ICD-10-CM, ICD-11 MMS, ICD-11 ICF, ICD-11 Foundation, ATC/DDD, ICPC-2, RxNorm, the DHD Diagnosethesaurus and Verrichtingenthesaurus, the G-Standaard, the Nederlandse Labcodeset, the NHG ICPC-1 to SNOMED CT map, and any FHIR CodeSystem, ValueSet, and ConceptMap resources. The code systems page lists each with its URI, versions, build command, and licence.

The console

Browse, look up, expand and translate

The console is its own program and image, ferroterm-console, beside the server. It reaches the server over the public FHIR API, so anything it does any FHIR client can do, and it edits the resources your deployment writes.

Run it

One binary and an index directory

The server and the build tool ship in one image and one tarball. The registry systems need nothing loaded; every other code system is an index you build once per release.

Docker

The first call

docker run of the published image serves UCUM, BCP 47, BCP 13 and ISO 3166-1 with no configuration, and answers a $lookup at once.

Compose

The quickstart

compose.yaml ships with every release. Point it at the index directory you built; the console profile adds the console.

OCI images

The container images

ghcr.io/ferrohealth/ferroterm and ghcr.io/ferrohealth/ferroterm-console, for amd64 and arm64, each with SLSA provenance and an SBOM you verify before you run it.

In the family

The product that serves the code systems

The FerroHEALTH products reach each other only over published protocols, and any FHIR client can use FerroTERM. These are the family's.

FerroEHR

The openEHR CDR validates the coded text of a composition against its terminology bindings through a FHIR terminology server.

FerroBRIDGE

The bridge asks for code systems and value sets through $lookup, $translate and $validate-code while it maps openEHR to FHIR.

FerroPIX

The patient index translates every HL7 v2 table value of its v2 face on a FHIR terminology server.
