- The SMART discovery document and the capability statement name the issuer `ferrohealth-smart`'s shared rule describes, never the first `[[auth.issuer]]` table, and `[auth] described_issuer`, which the server accepted without reading, now names it. Without the key the server describes the one issuer of kind `persons`, `patients` or `federation` whose metadata it holds, and a server that trusts only `machines` issuers, the usual terminology deployment, describes its one `machines` issuer for SMART Backend Services alone: the token endpoint, the client credentials grant and `private_key_jwt`, with no authorization endpoint and no `authorize` in the capability statement. Breaking: a server that trusts several such issuers and sets no `described_issuer` refuses the start, naming them and the key, and so does a `described_issuer` that names an unknown issuer, an issuer without metadata, or a `machines` issuer beside one that serves a user launch (#1250).
